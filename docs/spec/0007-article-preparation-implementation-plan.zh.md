## 1. 交付目标

按 [RFC 0006](./0006-article-preparation-and-management.zh.md) 完成单篇图文的新建／打开、字段、HTML 正文、配图、封面、显式保存和继续编辑。预览保留为后续独立能力，不纳入本次重设计的闭环，不新增联系人发送。

本文明确命令职责、运行时落点、任务依赖和停止条件。它不是实际账号写入授权，不安排发布、删除或多图文操作。

## 2. CLI 草案

沿用现有 `article` 与 `asset` 分组。下列为接口方向；首次保存和正文插图需完成页面能力核实，不能把命令存在当成能力已交付。

```text
mpctl article new
mpctl article open <candidate>
mpctl article inspect <article>
mpctl article inspect <article> --all > state.json
mpctl article update <article> --fields <json> --expected-hash <fieldsHash>
mpctl article cover <article> --asset <asset> --expected-hash <coverHash>
mpctl article check <article>
mpctl article save <article> --expect state.json

mpctl asset list <article>
mpctl asset upload <article> --file <image>
```

这些命令已有受限实现；本轮重做执行与结果语义、补首次保存和正文配图。`asset` 命令携带文章引用，复用明确编辑页及账号上下文，不新增隐式账号选择。素材选择歧义拒绝；具体插图入口由可靠平台路径决定，不先添加光标协议。

### 2.1 必要输入与输出

| 命令         | 成功输出方向                                               | 约束                                                                                        |
| ------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| new/open     | 当前 `article`、`bodyHash` 与请求结果                      | 首次成功直接交付，历史查询不复活旧引用，不隐含保存                                          |
| inspect      | 默认字段与 `fieldsHash`；`--all` 返回同文章的字段及三 hash | 完整读取检查观察稳定性，不承诺原子快照，不推断自动摘要                                      |
| update       | 实际 `fieldsHash` 与请求结果                               | 当前 title／author／summary，未提供字段不改，显式空字符串清空控件；不表示保存或服务器持久化 |
| cover        | 封面读取／设置结果及 `coverHash`                           | 来源明确、独立版本检查与回读；不与字段版本混用                                              |
| check        | `{ errors, warnings }`                                     | 空数组表达无已发现问题，不附 `ready:true` 或发布保证                                        |
| save         | 保存确认、保存后身份与有效引用、必要附带问题               | 首次保存处理身份转换；面板清理不覆盖保存事实；不附加刷新／重载／重开验收                    |
| asset list   | 供选择的素材候选与必要辨识信息                             | 分页未支持时拒绝或明确范围，不能把当前可见结果包装为全库                                    |
| asset upload | 确认的素材结果；有可靠证据时提供正文图片来源               | 上传不隐含插图或保存；thumbnail 不能冒充原图                                                |

首次保存改变定位时必须核实并交付新引用；若保存已确认但定位失败，分别报告，不重放 SAVE。历史结果不重新赋予旧引用写权限。错误沿用必要机器码与事实，主动作、交互问题和辅助清理可区分，不重复 message/action，不为所有错误自动补“读 help”。最终结果 schema 随业务切片修订。

### 2.2 字段与版本

字段读取使用 `title`、`author`、`summary`。`0.7.0` 分组修改接入这三个字段：非空 partial JSON，未提供字段保持原值，显式空字符串表示清空输入控件。标题使用已验证的原生可见编辑／受限 selection，等待 hidden mirror 只读确认，不写隐藏值、不调用编辑器内部对象；本次空标题 innerText 含换行，textContent 与隐藏提交值均为空，不将这种渲染差异误判为内容不同，也不规范化 fieldsHash 输入。`summary` 读取页面 digest 输入原值，不推断留空后的平台最终摘要。未知键、错误类型和所有字段明显非法值在写入前拒绝；不接受未定义语义的 `null`。

采用保守本地输入边界（title／author／summary 为 64／8／120 个 UTF-16 单元，标题和作者不接受换行，全部不接受 NUL），不是微信实际字符计数规则承诺。页面 `max-length` 属性只证明控件元数据，当前页面写入和云端持久化需分别验收。

首批使用 `fieldsHash`，仅覆盖 `[title, author, summary]` 三个实际读取的字符串，按该顺序 JSON 序列化后计算 UTF-8 SHA-256。保留字段空值、空格和 Unicode 原值；不对任意 DOM 序列化，也不把字段版本解释为封面或整篇稿件版本。

正文、字段和封面各自检查相关版本。SAVE 的 `--expect` 文件绑定同一 article 并提供三 hash，在实际派发前核对；不自动更新状态文件或采纳最新页面值。真正影响保存的其他设置若不在支持范围内，需要明确拒绝或纳入检查范围。上述检查均不是平台原子事务。

### 2.3 文件工作流示例

```text
open/new         → article、bodyHash；current 仅用于已有页接入／恢复
inspect          → title、author、summary、fieldsHash
本地编辑 fields.json 和 body.html
update           → 新 fieldsHash
push             → 正文写入并回读新 bodyHash
asset upload     → 已确认素材
正文配图          → 可靠图片来源写入 HTML 后 push，或显式原生插入；回读正文
cover            → 经核实的封面版本
inspect --all    → 本次准备保存的 state.json
save --expect    → 保存事实、保存后有效引用、必要附带问题
继续编辑／保存     → 验证首次保存后的目标与版本
```

正文图片优先复用 HTML 与整体 push，前提是平台提供可靠正文图片来源和必要元数据。若仅原生素材插入可靠，则实现显式插入并回读，不先设计通用光标／选区协议。不拿临时 Blob URL、猜测缩略图后缀或任意外链补位；上传成功本身不证明正文配图成功。

## 3. 运行时落点

| 位置                 | 负责的内容                                               | 复用／修改位置                                                     |
| -------------------- | -------------------------------------------------------- | ------------------------------------------------------------------ |
| contracts            | 输入、结果、错误 schema 与服务契约；二进制参数类型       | `packages/contracts/src/index.ts`                                  |
| CLI                  | Commander 命令、字段 JSON／图片文件读写和校验、紧凑输出  | `packages/cli/src/main.ts`、`article.ts`；文件逻辑按需要落独立模块 |
| broker               | 已准入会话的服务 Relay，不存素材或重编码图片             | `packages/broker/src/server.ts`                                    |
| background workspace | 文章定位、原子防重与结果存储、业务调用；不做历史全局准入 | `packages/extension/src/workspace.ts`、`pages.ts`、`operations.ts` |
| content              | 文档写协调、DOM 适配、原生回执与文档守卫，覆盖 MAIN 动作 | `entrypoints/mp.content.ts`；逻辑按任务落 `src/mp/`                |
| MAIN                 | 仅执行必须进入页面主环境的 handler／JSAPI                | 现有 `page-contracts.ts`、MAIN provider；必要时增方法              |

先沿现有 Workspace 入口增加业务方法，不为每个命令创建 Token、服务或 manager。字段 DOM 方法不自动加入正文 MAIN 服务；素材是否需要独立页面服务，由实际页面入口和使用者决定。

每个修改调用在所属编辑文档内协调，并在真正派发前重验目标和相关版本。不把串行队列解释为用户／微信也被锁住，不为完整发稿流程持有跨命令锁。协调必须覆盖实际页面执行端，BG 重启不能凭新空队列放行同文档冲突动作；MAIN 与 CONTENT 不能各自判断空闲。

请求记录负责同键防重，当前页面任务决定文档是否可写，SAVE 自己处理同稿远端请求的顺序风险。删除历史 `pending()` 驱动的全局准入；超时、清理失败和未知历史不自动阻止独立稿件。具体时序与迁移边界以 RFC 0008 为准。

### 4.2 必须验证的链路

```text
CLI Blob → IPC → broker Relay → WS → background
                               → Chrome → content（页面能力需要时）
                                        → 页面桥 → MAIN（确需主环境时）
```

通过真实 RPC 参数接收图片，并返回小型内容摘要供测试核对；不能只测 `IPort.postMessage(ArrayBuffer)` 或框架自己的单跳示例。

当前页面桥默认消息上限为 4 MiB、队列字节预算为 8 MiB，且只接受部分值类型。新版 Nexus 的 16 MiB 消息上限不覆盖这些本地限制。先确认 serializer 实际交给 Port 的载荷，再决定桥是否需要兼容修改；不能仅因业务参数是 Blob 就让桥绕过原有类型和大小检查。

验证包含 Blob 内容／MIME、独立文件名、非零 offset 的字节视图、跨分帧边界的载荷、嵌套二进制、Relay、大小超限、断线和关闭。消息大小按各跳编码后的实际字节检查；有界并发下记录内存峰值和控制命令可用性。产品大小预算在这些证据后确定，不直接开放框架上限。

不添加 mpctl 分片、base64、第二套 HTTP 上传或常驻二进制缓存。接收上下文需要临时 Blob URL 时，由创建方在使用结束／失败／失效后释放；这不是平台素材引用。

## 5. 页面能力核实清单

历史线索来自 `tmp/ref/editor-page-structure.md`，只用于找入口：

- 标题可见 ProseMirror 与隐藏 `#title` 曾有同步观察，直接写隐藏值曾异常；先确定真实读取和提交路径。
- `#author`、`#js_description` 曾可输入回读；重新读取默认提取摘要和规范化规则。
- 编辑器工具栏“本地上传”和图片库上传是不同入口。工具栏上传可能改变正文，不能据此实现无副作用的 `asset upload`。
- 图片库和封面选择的确认／下一步不同，需独立核实素材身份与裁切结果。
- 保存、预览只有入口观察；需确定成功／失败／处理中状态和保存后文章身份。

优先验证图片库的独立上传。如果所有可靠上传入口都会修改正文，记录此事实并重新评审命令语义；不把有副作用的入口伪装为纯上传，也不通过自动恢复原正文掩盖副作用。

核实可以先做既有页面只读观察。输入、上传、保存和预览发送必须取得指定测试稿／接收目标授权，不能拿现有稿件做写探针。只读观察或历史页面回读不是授权替代物。

## 6. 失败与不确定结果

| 失败位置                         | 必须保留的语义                                                                                 |
| -------------------------------- | ---------------------------------------------------------------------------------------------- |
| 本地字段／图片校验或目标核对失败 | 尚未派发远端修改；不自动导航到另一目标                                                         |
| 字段／封面版本不匹配             | `content_conflict` 或经契约确认的专用冲突码；该动作零写入                                      |
| 多字段执行中途失败               | 必要时附 title／author／summary 中实际确认或派发未知的字段；未派发字段不能包装为已写或结果未知 |
| 图片尚在传输时失败               | 若不能证明远端尚未调用上传，仍不能认定平台零副作用                                             |
| 上传／保存已派发但结果不明       | 返回该动作的未知事实，同键不重放；仅检查实际文档／控件或同稿保存风险                           |
| 清理失败                         | 保留原业务结果，另报清理问题；保存已确认不降级，后续按实际 UI 判断                             |

具体新增错误码随首个业务契约评审确定，不先建立通用错误分类系统。Result 贯穿读取、转换、状态编排与异步回调；Nexus 的 safe API 若可直接使用，优先使用，不再包一层仅改名字的服务包装。

作者／摘要修改采用 `invalid_fields`、`content_conflict`、`field_update_unknown`，成功仅返回 `fieldsHash`。内层 Chrome 调用派发后丢失回复也必须保留未知写入语义，不能在 workspace 回传普通 `page_failed` 掩盖。每个字段的原生 setter／事件派发前重验目标并重新定位控件；第一字段事件可能改变页面，整批执行前的检查不足以保护第二字段。原生 setter／事件构造能力缺失属于派发前失败，不使用 throw/catch 作为预期控制流。

第一字段派发后，第二字段即使因已知能力缺失而未派发，整次操作也不能回报普通零副作用失败。`updatedFields` 表示已通过目标守卫和回读确认的字段，`unknownFields` 仅表示已派发但未确认的字段；两者不要求覆盖全部请求。字段更新不是平台原子事务；已知部分成功也不得自动回滚或整批重试。

外层仅收到更新成功响应、随后目标校验失败时，若没有可靠的派发明细，则只报告 `field_update_unknown`，不把所有请求字段声明为已更新或已派发未知。字段名单是可选事实，不要求为了凑齐错误结构而编造；即使输入值本来相同也不会强制派发事件。

## 7. 任务图与退出条件

```text
平台能力核实 → 完整文章业务切片（含防重／文档协调）
            → 故障时序与跨稿隔离验证 → 旧记录兼容及废弃框架删除
```

| 阶段            | 工作                                                              | 完成条件                                                                     |
| --------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| R1 平台事实     | 首次保存信号、稿件身份／document 转换；可靠正文图片来源或原生插入 | 脱敏真实证据；未知项仅限制相关能力，现有二进制与字段证据按适用范围复用       |
| R2 业务闭环     | 新建、字段／正文、上传／插图、封面、完整读取、首次保存、继续编辑  | 防重与文档协调随业务落实；CLI 完整路径在授权测试稿通过，不先建设统一异常框架 |
| R3 故障时序     | 同页旧版本并发、回复丢失、动作晚到、BG 重启、执行端重挂载         | 同键不重复 native；同页不被旧动作覆盖；旧调用不能落到新实例                  |
| R4 独立性与结果 | A 稿未知、B 稿完整工作；同稿再次保存；清理／入账失败              | 只限制具体冲突；保留保存确认和原首因，存储失败不伪装成未执行                 |
| R5 迁移与删除   | 旧键防重／原结果查询、版本准入、废弃框架和专属测试删除            | 不清账本、不补判旧成功；新请求不再依赖历史 pending；真实闭环与关键回归仍通过 |

R2 接入新记录前先落实必要的旧键兼容与版本隔离，R5 完成剩余删除；不让两个执行模型同时写同一文档。旧记录具体迁移按 RFC 0008，不通过临时绕锁完成验收。

新测试加入正式入口，围绕上述用例与失败时序验证，不镜像旧状态矩阵。保留正文、文件安全、连接／broker 和实际副作用边界的独立回归。隔离测试不能替代真实平台验收。
