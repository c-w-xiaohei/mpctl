# RFC 0008：请求防重、页面执行与业务结果

- 状态：2026-10-14 修订方案，替换旧统一执行状态机设计；代码与旧账本尚未按本方案迁移。
- 创建日期：2026-10-10；修订日期：2026-10-14。
- 目标：完成文章创建、编辑、配图、显式保存及继续编辑；异常时限制实际受影响的动作。
- 关联：[通信架构](./0001-communication-architecture.zh.md)、[发稿准备需求](./0006-article-preparation-and-management.zh.md)、[实施方案](./0007-article-preparation-implementation-plan.zh.md)。

## 1. 修订原因与舍弃项

原始诉求是简化过度工程，并让副作用防重与异常处理联动。旧设计随后要求“无法证明新旧操作独立就拒绝”“只有原执行结束证据才能解除限制”。实现用 `operations.pending()` 驱动 `workspace.conflict()`，新建尚无文章绑定时，旧稿未决 SAVE 也会阻塞它。

旧方案已经区分效果和执行结束，但恢复条件依赖可能随页面销毁而永久丢失的证据。增加状态字段不能解决这个前提错误。

截至本次修订，协议 `0.15.0` 的实测是：旧 SAVE 保留 confirmed／persistence unverified，原失败为 `bg.reload / navigation_failed`；新建被它阻塞，未创建页面。首次 SAVE 和上传后正文插图仍有产品能力缺口。文档修订不改变这些历史事实，也不代表新方案已验收。

| 舍弃的方式                                                         | 替代方式                                                 |
| ------------------------------------------------------------------ | -------------------------------------------------------- |
| 扫描所有历史未决记录决定工作区准入                                 | 按实际文档、控件和同稿远端保存检查具体冲突               |
| `unresolved` 等价于持续占用资源                                    | 历史结果、当前执行、后续可操作性分别判断                 |
| 所有业务套 `accepted → issued → unresolved/settled` 及通用 `ended` | 持久登记只授予一次执行权，各业务解释自己的结果和残余影响 |
| `run/issue/checkpoint/bindTarget` 编排统一事务                     | 小型原子防重与结果存储；业务步骤留在所属能力中           |
| 保存、后续导航、清理共同决定保存成功                               | 保存事实与辅助问题分别返回，不把清理失败变成保存未知     |
| 要求新请求证明与全部历史相互独立                                   | 检查这个请求实际会接触的资源；未知历史不产生无边界占用   |
| 先完成异常框架，再补正常功能                                       | 先核实平台能力，交付完整文章路径，再以具体故障时序验证   |

## 2. 工作流与保证边界

```text
新建／打开 → 字段与 HTML 正文 → 上传并显式配图 → 封面
          → inspect --all → 显式 SAVE → 继续编辑
```

- `new/open` 首次成功直接交付当前文章引用；两条命令之间不持有工作流锁。
- 每次修改明确目标，在实际派发前核对登录、文档与相关版本；检查后写入不是平台原子 CAS，也不能锁住人工操作。
- 同请求不重复执行；同键异输入拒绝；未知请求不自动换键、续跑、回滚或重放。
- 正文、字段、插图、上传和封面不隐含 SAVE；不新增发表、联系人预览或批处理。
- 保存确认、保存后身份、当前页面可用性是不同事实。后台重启不等于旧任务停止，页面消失不等于云端请求取消。
- 不承诺微信端 exactly-once、跨设备去重，或由当前相同内容反推出历史操作成功。

## 3. 状态归属与运行时落点

沿用 CLI → IPC → broker Relay → WS → BG → CONTENT／MAIN。不增加进程、任务平台或第二套传输。

| 所有者                              | 保留的状态／责任                                    | 边界                                                 |
| ----------------------------------- | --------------------------------------------------- | ---------------------------------------------------- |
| CLI                                 | 本地文件、期望版本、本次请求 ID、结果展示           | 不判断远端任务已停止，不维护第二份业务账本           |
| broker                              | 配对、版本、会话及 Relay                            | 不重发业务、不推断结果                               |
| BG 防重存储                         | 请求 ID、输入摘要、唯一执行登记、必要目标及已知结果 | 不扫描历史决定全局可用性，不调度步骤                 |
| BG workspace／pages                 | 明确文章定位、当前引用、页面创建与接入、业务调用    | 引用不是持久权限；标签组只是页面组织，不是事务边界   |
| 文档执行入口及 CONTENT／MAIN 适配器 | 当前文档任务、执行实例身份、本地防重、原生回执      | 同一文档写协调覆盖实际执行端，不能仅依赖 BG 内存队列 |
| SAVE 业务                           | 必要的同稿未决远端保存事实                          | 只用于判断相关后续保存，不扩展为全局锁               |

文档协调优先收敛到现有 CONTENT 文档入口，MAIN 继续执行必须进入主环境的动作；跨 world 的调用、原生未完成事实都属于同一个文档协调边界。具体接线在首次实现中验证，不新增通用资源锁服务。

正文、字段、封面版本来自实际页面；不维护隐藏的“最近状态”替调用方决定保存。执行端回执可补历史事实，但不承担整篇文章持久备份。

## 4. 用例与时序决定行为

### 4.1 正常完成一篇文章

| 顺序 | 动作               | 完成本步必须交付                                     |
| ---- | ------------------ | ---------------------------------------------------- |
| 1    | 新建／打开         | 精确编辑文档、当前文章引用与正文版本                 |
| 2    | 编辑字段与正文     | 实际回读及相关新版本，不暗中保存                     |
| 3    | 上传               | 可验证的素材结果；缩略图不能冒充正文原图             |
| 4    | 正文配图           | 可靠图片来源经 HTML 写入，或显式原生插入；回读正文   |
| 5    | 设置封面           | 实际封面结果及版本                                   |
| 6    | 完整读取           | 本次准备保存的文章状态；读取稳定性检查不承诺原子快照 |
| 7    | 显式保存           | 原生保存事实、保存后身份和可用引用；附带问题单独说明 |
| 8    | 继续编辑并再次保存 | 有效目标与当前版本，验证首次保存后的完整路径         |

首次 SAVE 不能要求保存前已有已存稿 ID 或手动历史基线。需先核实成功信号、身份生成、URL／document 变化；历史手动操作线索不能直接当成当前 CLI 支持证据。

### 4.2 同页并发修改

```text
A 和 B 都读取 V1 → A 获得文档执行机会 → A 写成 V2
               → B 获得执行机会 → 重查版本 → 拒绝过期 V1
```

正文、字段、插图、封面与 SAVE 在同一文档内协调。等待前的版本检查不能代替临执行检查；不同文档不排进同一队列。跨标签确为同一保存目标时，远端 SAVE 顺序另按 4.6 处理。

### 4.3 原生完成，回复丢失

```text
K 登记 → 原生执行 → 确认 → 结果持久化 → 回复丢失 → 同 K 查询／重提
```

同键返回原结果，不再次 native。若在回执持久化前中断，查询存活原端回执并有界补记；回执也丢失则返回历史未知。回复丢失本身不让已结束的页面任务继续占用文档。

### 4.4 超时后原生动作晚到

```text
A 派发 → 等待超时 → B 请求修改同页 → A 仍可能改变页面
```

不能在 timeout／`finally`／Promise 返回时直接放行 B。原生适配器判断动作是否仍有迟到影响，必要时暂停该文档的冲突写入，独立文章继续。

自有业务停止后，迟到回执只补充事实，不再次触发剩余字段、清理点击或 SAVE。不同 API 的完成／取消语义各自验证，不强行规定一种通用结束证据。TTL、当前内容相同都不是动作停止证明。

### 4.5 BG 重启或页面执行端替换

```text
BG 登记 K → 页面执行 K → BG 重启 → 页面原任务仍可能继续
```

- 新 BG 不凭旧记录重新授权 K；查询仍可返回持久事实。
- 原文档仍在：重新接入其执行协调与回执。无法接入则该目标暂不可写，不影响其他独立文档。
- BG 重启不能产生第二个互不知情的文档队列；文档内原任务仍须约束新命令。
- 优先复用 document／executor 身份。旧 BG 的迟到调用不能自动绑定到替换后的执行实例；同 document provider 重挂载也必须验证。
- 替换执行实例不证明旧原生动作停止。同文档旧 MAIN 仍存活时，新入口须接入其活动事实或拒绝该文档写入，不能把空表当作空闲。
- 仅影响已销毁文档的任务与已经派发的云端请求分别处理。不得为了恢复而自动刷新、关闭或丢弃未保存内容。

### 4.6 A 稿保存未知，后续做什么

| 后续动作                  | 行为                                                            |
| ------------------------- | --------------------------------------------------------------- |
| 同键查询／重提 A 的 SAVE  | 返回原事实，不重新派发                                          |
| 新建独立 B 或编辑／保存 B | 检查自己的页面和实际共用控件，不因 A 的历史未知拒绝             |
| 编辑 A 的本地 HTML 文件   | 不受远端 SAVE 记录限制                                          |
| 编辑 A 的页面             | 检查原保存是否仍会改变当前文档／UI；不能仅看历史状态            |
| 再次保存 A                | SAVE 能力判断旧请求晚到是否可能覆盖新版本，必要时仅限制同稿保存 |

历史记录可以帮助识别具体远端风险，但 `unresolved` 标签不构成资源占用。存入同一个素材库也不意味着上传之间必然互斥；只有实际共享页面／控件才进行相应协调。

同稿 SAVE 的排序、确认或取消证据仍需平台核实。当前快照匹配、重复读取或页面销毁不能证明旧云端请求已经结束；证据不足时明确报告该稿再次保存的局部限制，不伪造自动恢复能力。

### 4.7 保存已确认，辅助步骤失败

```text
原生保存确认 → 关闭历史面板失败
```

返回“保存已确认；面板清理失败”。若未能取得保存后的文章身份，再单独报告引用不可用。不得降级保存事实，也不重放 SAVE。能否继续编辑由实际 UI／目标决定。

SAVE 不增加后续 reload、列表刷新或云端重开验收；首次保存由平台自身引发的身份／document 转换必须处理。独立持久化证据如存在可保留，但不是所有保存成功的附加门槛。

## 5. 最小防重路径

继续使用扩展私有 IndexedDB 短事务。职责只有原子登记、按原请求记录结果、查询；不新增存储适配框架，也不以另一套通用状态机取代旧状态机。

```text
校验请求身份／输入摘要
→ 原子登记：首次 / 同键同输入 / 同键异输入
→ 只有首次调用继续：取得实际资源执行机会
→ 临执行核对目标、版本与执行实例
→ 执行端本地防重 → 原生动作 → 业务回执 → 持久记录结果
```

登记可早于只读预检；关键是任何可能改变页面的步骤之前必须提交成功。打开素材弹窗也算页面动作。版本在等待后、真正写入前重验，不能用登记时的值代替。

- 事务 complete 才是许可；提交不明、存储失败时不派发。存储完全不可读会阻止依赖防重的新副作用，这是存储不可用，不是历史操作持锁；可独立读取的页面不因此封锁。
- 并发同键只有一个取得执行权；不同参数拒绝。存活同键任务可关联，不复制执行；执行端也须在异步让出前占住键，匹配原请求与实例。
- 摘要按原输入计算，不先解析可能失效的引用；BODY 使用实际 HTML 字节，字段区分省略与空值，上传核对字节和元数据，SAVE 使用调用方提供的状态。目标另存。
- 已登记但尚未派发就崩溃，也不恢复执行许可；有明确未派发证据就保留，否则报告未知。无需为了把所有中断分类得更细而保留通用 accepted／issued 两阶段编排。
- 结果按同一 ID／输入／执行身份校验后记录，确认事实不倒退；矛盾回执报告问题，不 last-write-wins。部分字段、实际 hash、素材确认等由业务产生，不由存储层推算。
- 回执存储失败时报告已观察但未持久化的事实；同键不重做。页面占用按实际执行判断，同稿 SAVE 仍检查远端顺序风险。不能从写库失败直接推导全局锁。

业务调用保持有类型的方法，不改成 `execute(kind, unknownPayload)`。存储 API 不接受步骤图、不要求业务提供通用 `ended`，也不提供供全局准入使用的 `pending()`。

## 6. 结果、查询与 CLI

分清三类信息：原业务事实、本次通信／存储问题、辅助 UI／定位问题。保存确认后清理失败不能变成“是否保存未知”；查询失败也不能覆盖原失败原因。

- `operation status <id>` 先读持久记录，不要求旧文章引用有效；可有界读取原实例已有回执，不调用 native、导航或重新执行。
- 查询成功只表示取得历史事实，不等于业务成功。查询不到记录也不能证明原 submit 未在途中；不据此换键。
- 每次业务请求在派发前具有 ID；CLI 允许 `--operation`，自动生成时先输出可恢复的标识，stdout 保持结果 JSON。不新增 CLI 票据库。
- 历史结果不返回可复活的文章／素材句柄。需要继续编辑时重新接入当前目标；首次成功的 `new/open/upload` 仍直接交付当前引用。
- 新稿首次保存须分别报告保存确认与保存后引用。已确认保存但引用获取失败时，仍保留保存事实并指导只读接入，不再次 SAVE。
- 最终 wire schema／退出码随业务切片一起更新：未知或主动作失败非零；单纯辅助清理失败不能抹掉已确认的主动作。机器输出必须让调用方区分两者，不能只换错误文案。
- 错误经过合法业务边界保留首因，在真正的输入／传输／出站处校验；不逐层复制错误白名单或封套。私有 URL、凭据、正文、动态身份不进入公开诊断。

## 7. 迁移与删除边界

| 现有位置                       | 调整                                                                        |
| ------------------------------ | --------------------------------------------------------------------------- |
| `operations.ts`                | 收窄为原子防重、业务结果及查询，移除通用执行回调／checkpoint／资源释放职责  |
| `workspace.ts`                 | 删除 `pending()` 驱动的通用冲突判断；保留定位、版本和业务编排，接入文档协调 |
| `mp.content.ts`、`mp/jsapi.ts` | 收敛同文档写入口、防重、实例校验与迟到回执，覆盖 BG 重启                    |
| `mp/article-save.ts`           | 首次保存及身份转换；保存确认与辅助问题分开；处理同稿远端顺序风险            |
| 上传／素材适配器               | 补可靠正文配图路径，不将 thumbnail 推算成原图                               |
| contracts／CLI                 | 随业务切片更新结果语义，不要求调用方理解内部 owner、账本代次或状态矩阵      |

原记录保留 ID、输入摘要、已知效果、首因和历史状态，不批量改成成功／已结束，不清库或换键绕过。旧 `bgEffects: pending` 只记录历史缺口，不自动成为新建许可的前提；遗留活动页面／导航和远端 SAVE 风险按其实际目标评估。

旧协议解码限于兼容读取和防重；不得为了兼容把旧执行引擎继续作为新请求的默认路径。已用键在迁移后仍不能重新取得执行权。现有键代次与安装隔离先保留为内部兼容约束；不自动裁剪、轮换或重新认领旧键。

迁移前确定新旧记录识别及版本准入，保留原记录并验证旧键、结果查询和错误首因；损坏／不兼容记录不清空后继续。具体 schema 变更随实现评审，本次文档不执行迁移。保持 CLI、broker、扩展协议一致，避免两个执行模型同时写同一文档。

## 8. 实施与验收

1. 先核实首次 SAVE 的确认／身份转换，以及正文配图的可靠平台路径。
2. 在完整文章路径所需的业务切片中落实防重和文档协调，取得创建、排版、配图、封面、首次保存、继续编辑的真实证据；不先建通用异常框架。
3. 验证同页旧版本并发、回复丢失、迟到原生动作、BG 重启、同 document 执行端重挂载及旧请求晚到。
4. 验证 A 稿异常时 B 稿仍能完整工作；另验同稿再次 SAVE 的顺序风险、保存成功而清理失败、回执写库失败。
5. 迁移所需旧记录查询／防重并删除被替代执行框架；删除只镜像旧状态矩阵的测试，保留有独立价值的故障时序回归。

隔离测试覆盖实际 CLI → broker → 扩展 → 页面边界；真实样本验证平台行为，两者不可互相替代。只在已授权测试稿和动作范围内验证；本文不是新建、上传、保存或清理真实环境的授权。

| 增长轴                                       | 变化应落在哪里                                 | 不引入的结构                       |
| -------------------------------------------- | ---------------------------------------------- | ---------------------------------- |
| 新增文章方法，例如插图                       | 该能力的原生动作、版本与确认逻辑，复用文档入口 | 全局状态转换分支                   |
| 新增素材能力组                               | 素材身份、结果和实际页面资源                   | 素材库全局锁、策略注册表           |
| 新稿变已存稿这一资源关系                     | SAVE 的身份转换与文章定位                      | 新的会话／工作流对象               |
